# CLAUDE.md

Developer notes for `openvpn-on-demand`. User-facing docs: [`README.md`](README.md). Marketplace-wide conventions: repo-root `CLAUDE.md`.

## Shared client support

This plugin supports Claude Code and Codex. `plugin.json` is the portable Codex manifest; `.claude-plugin/plugin.json` is the Claude manifest. Both catalogs and both manifests must agree on name, description and version. Setup/doctor procedures live in the named skills; `commands/` contains Claude wrappers. Keep changes to the shared procedures in `skills/`, not in those wrappers.

## Layout
- `servers/openvpn/` — MCP server (uv project; package `openvpn_mcp`, script `openvpn-mcp`, Python ≥ 3.10). Four tools: `vpn_status`, `vpn_connect`, `vpn_connect_ephemeral`, `vpn_disconnect`. Launched by `.mcp.json` via `scripts/launch.sh`. Two backends, chosen once at import in `server.py` (`_select_backend`; `OPENVPN_OD_BACKEND` forces one):
  - **openvpn3** — the code in `server.py` itself: openvpn3's D-Bus services via the `openvpn3` Python module + `dbus-python`. Picked whenever those import.
  - **openvpn2** — `ovpn2.py` (unprivileged: reads unit state with `systemctl`, calls the helper through `sudo -n`) and `ovpn2_helper.py` (root side: profile allowlist, transient unit, route check). Picked when the host has no openvpn3 at all (no `openvpn3` on `PATH`) and `/usr/sbin/openvpn` exists; openvpn3 installed but not importable is an error, not a fallback. `server.py`'s `_ovpn2_*` functions map it onto the same result models; each tool starts with an `if BACKEND == "openvpn2"` dispatch, so the openvpn3 code and its tests are untouched.
- `servers/openvpn/src/openvpn_mcp/ovpn2_helper.py` — the only code that runs as root. Run **by path** under the system `python3` (`sudo -n /usr/bin/python3 -I …`, or a root-owned copy at `/usr/local/libexec/openvpn-on-demand/ovpn2-helper`), and imported by `ovpn2.py` for its read-only functions. Same constraints as `dnscheck.py`: stdlib-only, **Python 3.9 syntax**, no relative imports; `tests/test_ovpn2_helper.py` guards them. `ovpn2.py` refuses to start a tunnel through an installed copy that differs from the bundled file at all (`helper_state`), so a plugin update means re-running the install line; `down` still goes through a stale copy (it vets nothing, and under a restricted sudoers rule it is the only way to close a tunnel). `probe` (doctor/setup) is read-only: it *asks* `sudo -n -l`.
- `servers/openvpn/src/openvpn_mcp/dnscheck.py` — host DNS check (checklist check 9, the skill's post-connect check). Not imported by `server.py`; doctor, setup and the skill run it **by path** with the system `python3`, so it stays stdlib-only, Python 3.9 syntax (Amazon Linux 2023's `python3`), no relative imports (`-m` would import `__init__` → `server` → `mcp`). `tests/test_dnscheck.py` guards all three. On a host without openvpn3 it takes a different branch (`decide_host_resolver`): the VPN leaves DNS alone there, a hostname is judged by what programs get, and no fix is printed. Exit 0 OK / 1 FAIL / 3 WARN / 2 bad usage. Whether the 127.0.0.53 stub listens is asked of systemd-resolved itself (`busctl … DNSStubListener`); a DNS probe decides only where it can't say, because an unanswered probe also happens in a sandboxed shell on a host whose stub is fine. `--connected` (skill, after connecting) judges a host no tunnel domain covers by what programs get; `--url-stdin` reads the host from a credential URL on stdin without ever printing it; the script never echoes its arguments.
- `skills/vpn-on-demand/SKILL.md` — policy layer: decides *when* Claude calls the tools and which mode the project uses. Owns connect *and* disconnect; no safety-net hook, so a tunnel orphaned by a crash needs `openvpn3 session-manage --disconnect --config <name>` by hand (openvpn2 tunnels close themselves: idle limit, lifetime limit, no reconnect). It learns the backend from the `backend` field of `vpn_status` / connect results.
- `commands/setup.md` + `commands/doctor.md` — `/openvpn-on-demand:setup` (interactive configurator) and `/openvpn-on-demand:doctor` (read-only health check). Both read `setup-checklist.md` (9 checks; 1 decides the backend, 2, 4 and 7 have a variant per backend); doctor restates the list in step 2, so renumbering means editing both (a49e226 missed that). Prose plus `dnscheck.py` and `ovpn2_helper.py probe`; neither runs anything through `sudo` or calls `vpn_*` tools. A new command in a check needs an exact-match `allowed-tools` entry in both wrappers.
- `.claude/openvpn-on-demand.local.md` (consuming project) — per-project settings. Frontmatter: exactly one of `profile_name` (BYO) / `ovpn_provision_cmd` (ephemeral); optional `post_connect_cmd`, `post_disconnect_cmd`, `config_overrides`. Re-read every turn, so edits apply immediately — except that a `config_overrides` key removed in BYO mode stays in the profile (the stateless server only calls `SetOverride`, never `UnsetOverride`).

## Commands

```bash
cd servers/openvpn
make check                                               # ruff + format check + ty + pytest; D-Bus / openvpn3 / systemd / sudo / ip are all faked
python3 src/openvpn_mcp/dnscheck.py [HOSTNAME]           # host DNS check against this machine (read-only)
python3 src/openvpn_mcp/ovpn2_helper.py probe            # OpenVPN 2 backend prerequisites on this machine (read-only)
make tidyup                                              # ruff autofix + format
uv run openvpn-mcp                                       # stdio server (expects an MCP client)
claude --plugin-dir /absolute/path/to/openvpn-on-demand  # load into a live session
```

## Gotchas
- **Don't reduce `scripts/launch.sh` to a plain `uv run`.** `dbus` / `openvpn3` come from system site-packages, invisible to uv's managed interpreter; the venv needs `uv venv --python /usr/bin/python3 --system-site-packages`. Where `/usr/bin/python3` is older than 3.10 (Amazon Linux 2023: 3.9) the launcher builds the venv on a uv-managed Python instead, **pinned** (`managed_python`): uv's default is the newest CPython, which the lock may have no wheels for (3.15 tried to build `rpds-py` from source). It replaces a `.venv` whose `pyvenv.cfg` doesn't fit the host. `OPENVPN_OD_SYSTEM_PYTHON` overrides `/usr/bin/python3`; it exists so `tests/test_launch.py` can run both branches against stub interpreters, not as a user setting. Don't add a `.python-version` file: `uv sync` would then replace the system-site venv on Ubuntu.
- **The OpenVPN 2 helper is the trust boundary.** With a sudoers rule limited to it, whatever it accepts on stdin runs as root's OpenVPN. Keep the profile check an allowlist that rewrites the profile from parsed tokens (`sanitize_profile`): a deny-list misses `setenv opt up …`, quoting and `--up`; a new directive goes on `_DIRECTIVES` with an argument check, never a path-valued or script-running one. Pull filters go *before* `--config` (first match wins), the backend's own options *after* it (last one wins). The filters are **default-deny** (`PULL_ACCEPT`, then `ignore ""`): OpenVPN matches a filter against the raw pushed text, so a deny-list falls to `"redirect-gateway" def1`. OpenVPN installs **no routes** (`--route-noexec`); the helper parses the PUSH_REPLY from the unit's journal (all of that run's lines: a capped read loses the first parts of a long reply) and adds the private prefixes itself with `dev <tunnel>`, so nothing it causes can outlive the device or land on the host's own interface. The pushed `ifconfig` is the one thing the server still decides, and the kernel acts on it before the helper looks: the route it creates has metric 0 (above the host's own routes on Amazon Linux, which carry 512), so `demote_connected_routes` re-keys it to `ROUTE_METRIC` and `tunnel_violations` refuses any tunnel route below that; a prefix or tunnel network inside one the host is attached to (`host_networks`) is left out or refused. `close_ipv6` sets `disable_ipv6` on the device as soon as it exists: a tun device takes router advertisements, and one sent down the tunnel *after* the one-time check would give the host an IPv6 default route. `systemctl` saying a unit is `active` only means OpenVPN parsed its options — the tunnel is up when `StatusText` is "Initialization Sequence Completed" (`unit_state`), and usable once `/run/openvpn-on-demand/<name>.ok` exists (`describe`): the helper writes it after its checks, and a connect is commit-confirm (rollback timer armed first, cancelled last). `up` and `down` hold one lock (`/run/openvpn-on-demand/.lock`), and a name that is already taken comes back as status `exists`, which `server.py` treats like any tunnel found under the name. **The signal handler only takes a note** (`_interrupt`); `up` acts on it at `_checkpoint()` calls between its steps. Don't make it raise: an exception thrown from a handler lands inside the clean-up of an earlier signal (sudo relays a signal the helper also got directly; systemd follows SIGTERM with SIGHUP) or inside `subprocess` with a lock held, and both left tunnels, timers or a hung helper behind. No checkpoint goes between arming the timer and `systemd-run` returning, none after the `.ok` marker is written, and none in code the clean-up runs.
- **No DNS on the OpenVPN 2 backend, on purpose.** OpenVPN 2.6 ignores pushed DNS without a script; adding one means `script-security 2` as root and, on a host whose `/etc/resolv.conf` is systemd-resolved's uplink file, rewriting the resolver list of a machine that may only be reachable over the network. OpenVPN 2.7 runs a DNS script by default, which is why `SUPPORTED_VERSIONS` stops at 2.6 until that is tested.
- **SELinux enforcing is untested for the OpenVPN 2 backend.** On Amazon Linux 2023 (permissive) the unit logs two denials that would bite: `nnp_transition` (with `NoNewPrivileges=true` the process can't enter `openvpn_t`) and reads of the profile under `/run/openvpn-on-demand` (labelled `var_run_t`; `openvpn_t` may read `/etc/openvpn` and `/run/openvpn`).
- **Test the OpenVPN 2 backend for real in a container, not on your network.** The unit tests fake systemd. An AL2023 container with systemd as PID 1 (`--cap-add NET_ADMIN --cap-add SYS_ADMIN --device /dev/net/tun --cgroupns=private`, never `--privileged` or host networking), a second container as OpenVPN server, and an MCP stdio client against `launch.sh` exercise the whole path. A Docker container differs from an EC2 host in two ways that hid bugs: its routes have metric 0 (re-add them with `metric 512` to see what a tunnel route at metric 0 takes over), and new devices come up with IPv6 off and `/proc/sys` read-only (`mount -o remount,rw /proc/sys` inside the container, then `net.ipv6.conf.default.disable_ipv6=0`, to exercise `close_ipv6`; only touch `net.*` there, the rest of `/proc/sys` is the host's).
- **Never pre-parse `.ovpn` files with `openvpn3.ConfigParser`.** Its directive whitelist rejects valid configs (AWS Client VPN's `remote-random-hostname`). Hand raw bytes to `ConfigurationManager.Import` over D-Bus; openvpn3's parser is authoritative. Shipped broken in 0.4.0.
- **DNS has two layers; `netcfg.json` only proves the first.** openvpn3-service-netcfg pushes the tunnel's DNS into systemd-resolved; programs must still *ask* it (nss-resolve, or `/etc/resolv.conf` = the 127.0.0.53 stub). If Tailscale, a VPN client or NetworkManager owns `/etc/resolv.conf`, `resolvectl query` works while `getent` gets `0.0.0.0` (rebinding-protected resolvers) and clients hang on local services; Tailscale can stay stuck owning it after an unclean stop (tailscale/tailscale#19062). `dnscheck.py` detects this; the plugin prints fixes, never runs them.
- **AGPL-3.0-only.** The openvpn3 backend links the AGPL `openvpn3` Python module. New Python/shell files start with `# SPDX-License-Identifier: AGPL-3.0-only`. `server.py`'s `main()` prints the AGPL §5(d) notice to **stderr** — stdout is reserved for the MCP stdio protocol.
- **Version bumps:** update both marketplace catalogs, both plugin manifests and any in-tree Python project/lockfile. `scripts/check-version-sync.sh` checks metadata and package paths; `uv sync --locked` checks Python lock consistency.
